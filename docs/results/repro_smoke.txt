G. README GAPS / FAILURES (each with the exact fix that worked)
================================================================================

G1. Port is not actually configurable through .env (README §4.1 table, and the
    sentence "PGHOST, PGPORT, PGDATABASE | 127.0.0.1, 55432, shopdb").
    Fact: scripts/start_cluster.sh computes `PORT="${PGPORT:-55432}"` (line 12)
    BEFORE it sources .env (line 18), so at initdb time only the *exported*
    shell variable matters. Editing .env alone silently leaves the cluster on
    55432 while setup_db/collector/dashboard connect to .env's PGPORT.
    Evidence: PORT_before_sourcing_env=55432 PGPORT_after_sourcing=55433.
    Exact fix that worked: `export PGPORT=55433` in the shell before
    `scripts/start_cluster.sh`, *and* `PGPORT=55433` in .env.
    Suggested README edit (after §4.1 table):
      "The cluster port is read from the environment at init time. To use a
       different port, `export PGPORT=55433` before `scripts/start_cluster.sh`
       and set the same `PGPORT` in `.env`; editing `.env` alone is not enough."
    Suggested code fix: move `set -a; . ./.env; set +a` above `PORT=...` (guarded
    by `[ -f .env ]`), then the README table becomes true.

G2. start_cluster.sh cannot initialize the cluster when Git Bash's mktemp
    returns an MSYS /tmp path (README §3 promises "Git Bash (bash, mktemp, sed)"
    is sufficient).
    Exact error: initdb: error: could not open file "/tmp/tmp.ffo4ThindV" for
    reading: No such file or directory
    Cause: scripts/start_cluster.sh:19 `pwfile="$(mktemp)"` produces
    `/tmp/...`; native initdb.exe cannot open it when MSYS path conversion is
    off. No .pgdata was created, so the retry was clean.
    Exact fix that worked: `export TMPDIR='C:/Users/johnq/.../tmppw'` (any
    native Windows directory) before running the script.
    Suggested README edit (Prerequisites table, Ports row area):
      "Git Bash must be able to hand native Windows paths to the PostgreSQL
       binaries; if your shell sets TMPDIR=/tmp, run
       `export TMPDIR=\"$LOCALAPPDATA/Temp\"` first."
    Suggested code fix (one line): `pwfile="$(mktemp ./.pgpw.XXXXXX)"` — a
    relative path inside the repo is readable by initdb.exe on every Git Bash.

G3. README §6 omits the test databases entirely (biggest gap).
    §6 says only `.venv/Scripts/python.exe -m pytest tests -v`. On a fresh
    cluster that run fails: `2 failed, 16 errors`, first error
    `FATAL: password authentication failed for user "postgres"`.
    tests/conftest.py:4-7 requires shopdb_t2; tests/test_alert.py:4-5 requires
    shopdb_t3.
    Exact fix that worked: `scripts/setup_db.sh shopdb_t2` and
    `scripts/setup_db.sh shopdb_t3` before pytest, then 18 passed.
    Suggested README edit, replace §6 body with:
      ```bash
      scripts/setup_db.sh shopdb_t2     # tests/conftest.py
      scripts/setup_db.sh shopdb_t3     # tests/test_alert.py
      .venv/Scripts/python.exe -m pytest tests -v
      ```
      and replace the `TBD-VERIFY` sentence with the observed result:
      "18 passed (9 alert, 3 capture, 6 privilege)."

G4. UNRESOLVED: two consecutive pytest runs after the databases existed failed
    with `password authentication failed` for all three roles (13x postgres,
    3x monitor_reader, 2x shop_app), although `psql` with the same .env
    credentials connected successfully at the same moment and an identical
    re-run minutes later passed 18/18 (twice, including from a clean subshell).
    Root cause not isolated; recorded here rather than guessed.
    Contributing hazard: scripts/dbconf.py:31 lets any `PG*` variable in the
    caller's environment override the corresponding `.env` value
    (`env.update(... k.startswith("PG"))`), so the effective connection
    parameters depend on the shell, not just on `.env`.
    Exact fix that worked: run pytest from a shell where the `.env` values are
    exported (`set -a; . ./.env; set +a`) or where no `PG*` variables exist.
    Suggested README edit (§6): "Run the suite from a shell with no PG*
    variables set (or with the .env values exported); dbconf merges ambient
    PG* variables over .env."
    Suggested code fix: in scripts/dbconf.py `load_env`, only take the password
    keys and PGHOST/PGPORT/PGDATABASE from os.environ if `.env` lacks them.

G5. Piping start_cluster.sh to `tee` hangs in Git Bash on Windows (the started
    postgres server inherits the pipe, so tee never sees EOF). The run was
    killed at its 300 s timeout and the cluster died with it; no data was lost
    (restart was clean).
    Exact fix that worked: `scripts/start_cluster.sh > log 2>&1`.
    Suggested README edit (§4.2): "Redirect the script's output to a file
    (`scripts/start_cluster.sh > start.log 2>&1`) rather than piping it;
    piping can hang because the server inherits the pipe."

G6. Minor: README §4.1 says `scripts/setup_db.sh` can generate `.env` itself,
    but the generated file hardcodes `PGPORT=55432`
    (scripts/setup_db.sh:18). With G1 this means the generated `.env` can never
    select a different port. Same fix as G1.

G7. Not a failure, for the record: README §5.4's order (start the lock demo
    after the collector has taken at least one snapshot) reproduces exactly;
    with `--hold 60` and a 15 s interval the sequence fire -> resolve completed
    in six snapshots. `README §12` cleanup (`stop` + `rm -rf .pgdata`) worked
    verbatim.
